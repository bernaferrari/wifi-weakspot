# Implementation plans: WiFi Weakspot (Android app)

Generated by the improve skill on 2026-11-10, at commit `918ea41c` plus the
owner's uncommitted working tree.

Audit scope: the Android app's own code (`composeApp/src/main/kotlin`,
`composeApp/src/androidMain/kotlin`, `androidApp/src/main`). Build files,
dependencies, CI, fastlane, scripts, the store listing and the web demo were
excluded at the owner's request. Nothing was built or run while planning:
every command in these plans comes from `docs/DEVELOPMENT.md` and is
unverified, and anything that depends on a real phone is marked as needing a
device check.

Each plan is self-contained: an executor needs only the plan file and the
repository. Plans do not push or open pull requests.

## Dependency notes

- **002 needs a commit from the owner first.** When these plans were written,
  the first half of removing background alerts (manifest entries, the
  dependency-injection binding, the Settings section) existed only as
  uncommitted changes. Plan 002 checks for that half and stops if it is
  missing. It also edits `PRIVACY.md`; the owner should read that diff and
  confirm the effective date before release.
- **006 after 002.** Both edit `Platform.kt` and
  `AndroidPermissionLaunchers.kt`. Plan 006 is written to work whether or not
  002 has run, but running them in order avoids a merge conflict.
- **008 after 003 and 001.** 008 edits the same function as 003
  (`settledOrder`) and assumes 003's version; it checks for it and stops
  otherwise. 001 and 008 edit different parts of `AnalyzeScreen.kt`.
- **005 and 006** are independent of each other but fix the same feature
  (floor-plan photos); test them together on a device.
- **004 and 007** are independent of everything else.
- Plans 002, 007 and 008 each touch all ten translation catalogs, in different
  files (Settings + Domain, History, Analyze), so they do not conflict.

## Direction ideas considered and not planned

- **Entering the real size of a home for the map.** The heat map only uses the
  map's proportions, which plan 005 now takes from the photo. A size setting
  would add a screen and change nothing visible. Worth doing only together
  with a scale bar or distance read-outs.
- **"New since last scan" badge on Devices.** On Android 10 and later the app
  cannot read hardware addresses, so a device is identified by its IP address,
  which routers reassign. The badge would regularly call a familiar device
  "new", which is alarming in a security-flavoured screen.
- **Exporting history.** Reasonable, but there is no obvious single format for
  four kinds of entries; needs a product decision first.

## Findings considered and rejected

Listed so they are not re-audited from scratch.

Looked at and left unranked (true or plausible, but not worth a plan now):

- Hardware address and vendor are never filled in for devices on Android 10+ — a platform limit.
- Root-mode quirks on Android 9 and 10.
- Room readings would be wiped if their stored JSON failed to decode — no way to trigger it was found.
- A crash and locale-dependent dates in the CSV export code — that code has no caller.
- Oversized values in a hand-crafted backup file.
- The "Wi-Fi is off" message can be stale after Wi-Fi is switched on from quick settings.
- About 440 fully-qualified names written inline instead of imported — style only; the plans tell executors neither to copy nor to rewrite them.

Raised by the audit and rejected on checking the code:

- A reported crash in an export path — no caller reaches it.
- Ordering of `lastSnapshotAt` updates in the Networks view model.
- A start-up race in the Devices view model.
- Duplicate keys among the "fact" labels in network details.
- Day-label collisions in History.
- An un-remembered `groupBy` in History; missing `contentType` on lazy lists.
- Duration of the device sweep.
